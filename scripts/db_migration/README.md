# DB reset — wipe data sources, keep everything else

Rebuilds the database from scratch while **preserving** all admin/responder/
notification/config data and **wiping** the three sensor data sources plus their
daily summaries (which get regenerated by the seeder).

| Wiped & regenerated | Preserved |
|---------------------|-----------|
| `sensor_readings` | `admin_users`, `admin_audit_logs`, `refresh_tokens`, `password_reset_otps` |
| `model_readings` | `locations`, `sensor_devices`, `camera_devices` |
| `weather` | `responders`, `groups`, `responder_groups`, `responders_otp_verification` |
| `daily_summaries` | `notification_templates`, `notification_dispatches`, `notification_deliveries` |
| | `acknowledgements`, `push_subscriptions`, `system_settings` |

## How this interacts with the app's auto-seeder

On every Docker boot, `scripts/start.sh` runs `alembic upgrade head` then
`scripts/seed_db.py`. `seed_db.py` is **idempotent** — it inserts a superuser,
3 notification templates, 2 system settings, 1 location, and 1 sensor + camera
device only if they don't already exist.

`load_preserved.sh` accounts for this:

- It **truncates** the 17 preserved tables before loading, so any base-seed rows
  the app already inserted are cleared first — no PK/unique collisions.
- After the preserved data is loaded, future app boots run `seed_db.py` again,
  but every base record now exists (from the old DB), so it cleanly no-ops.

You can run the migration before or after the app first boots against the new
DB — either way works. Just don't run `load_preserved.sh` while the app is
**live and writing** to that DB; do it before pointing the app at it, or during
a maintenance window.

## Requirements

- `pg_dump` / `psql` installed locally, with `pg_dump` major version **>=** the
  Railway server's Postgres version. On a version mismatch, prefix the dump
  command with `DUMP_VIA_DOCKER=1` to run `pg_dump` through Docker instead.
  (`psql` works fine across versions, so the load step needs no Docker.)
- The project virtualenv active (Alembic must be importable).
- The **old** DB should be at the latest Alembic revision — its schema must
  match what `alembic upgrade head` produces, since the dump is data-only.

## Steps

```bash
# 1. Dump the data to keep from the OLD database (use the Railway PUBLIC url).
#    Add DUMP_VIA_DOCKER=1 if your local pg_dump is older than the server.
DUMP_VIA_DOCKER=1 ./scripts/db_migration/dump_preserved.sh "postgresql://OLD_USER:PASS@OLD_HOST:PORT/railway"
#    -> writes scripts/db_migration/preserved_data.sql

# 2. Provision a NEW Postgres (new Railway service / database).

# 3. Build the new DB: schema (Alembic) + truncate base-seed + load preserved.
./scripts/db_migration/load_preserved.sh "postgresql://NEW_USER:PASS@NEW_HOST:PORT/railway"

# 4. Regenerate the data sources + daily summaries.
DATABASE_URL="postgresql://NEW_USER:PASS@NEW_HOST:PORT/railway" python scripts/seed_dummy_readings.py
```

Then point the app's `DATABASE_URL` at the new database.

## Notes

- The dump is **data-only** and uses `--disable-triggers`, so FK ordering during
  load is not a concern. The connecting user must own the tables (Railway's
  default user does).
- `alembic_version` is intentionally **not** dumped — `alembic upgrade head`
  sets it correctly on the new DB.
- Sequences for the preserved tables are restored (`setval`) by the dump, so new
  inserts won't collide with existing IDs.
- `preserved_data.sql` contains real user data (hashed passwords, phone
  numbers). It is git-ignored — do not commit it; delete it when done.
- The seeder uses `LOCATION_ID = 1` and expects a sensor device and camera
  device for that location — both come from the preserved data (the old DB's
  location keeps its original id).
